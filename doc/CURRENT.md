The rows below describe supported subsets. Each is the scope the reader
actually implements, not a claim of complete format coverage.

**For the list of formats this build can actually open, ask the binary:**

```
xfileunpackerc -i
```

With no file, `-i` prints every container type the build recognises, grouped
into one table per **carrier/target class**, with the `ID` each row can be
forced with via `-F/--filetype`. Given a file, `-i` still describes that file.

### What the tables are

A type appears in **every** table whose carrier it fits, so UPX is listed once
under *COM packers*, once under *MS-DOS packers*, once under *PE32 packers*
(as `PE32_UPX`), once under *PE64 packers* (as `PE64_UPX`) and once under
*Packers on other carriers* - printing it in only one of those would make the
other four tables wrong. The trailing `N format(s) in M table(s)` line counts
**distinct types**, not the sum of the table sizes.

The reference build (`USE_ARCHIVE` + `USE_STATICUNPACKER` + `WITH_XEMULATOR`)
prints 485 types in 21 tables:

alone. `PE32_INSTALLSIMPLE` / `PE64_INSTALLSIMPLE` are listed only when the
build also carries XEmulator, because their reader is compiled only then.

**A carrier table is not the complete set of formats of that kind.** A type is
placed by the carrier the registry records for it, and a type with no recorded
carrier keeps the category it always had - which for most legacy containers is
*Archives and containers*. `IZPACK`, `MAKESELF`, `WARPIN`, `GKSETUP`,
`MAXIS_MXS`, `IS7_INX`, `IS11`, `INSTALLSHIELD_BOOT` and
`INSTALLSHIELD3_ARCHIVE` are installers this build opens, and every one of them
prints under *Archives and containers* rather than under *PE32 installers*.
The console header says the same thing, so the table cannot be read as a
complete inventory by accident.

* **ID** - the token `-F/--filetype` accepts. Never wrapped or truncated.
* **Format** - the display name.
* **Versions** - the format versions, levels or revisions the reader handles.
  Where a version needs an optional component, the cell says so:
  `PE32_ASPACK` decodes 2.11/2.11r and 2.11c/2.11d only in a build with
  XEmulator, because those two stubs wrap their head in a per-file
  polymorphic self-decryptor.
* **Codecs** - what the reader decodes. `as ZIP` means the type is a wrapper
  that delegates to the named reader and inherits its codec list exactly.
* **Not supported** - what the *format* defines and this build **refuses**.
  The refusal can happen at detection (the file is not claimed at all) or at
  extraction (the member fails closed); either way nothing is silently
  mis-decoded. `SQUASHFS` decodes zlib and LZMA and refuses XZ, LZO, LZ4 and
  Zstandard; `WIM` decodes Store/XPRESS/LZX and refuses LZMS; `ZIP` refuses
  ZIP64 and multi-disk archives; `PE32_ASPACK` does not recognise a 1.x stub
  at all.

Every populated cell was read out of a dispatch arm that runs. A name in an
enum, a string in a display table, an entry in a trial-order array and a
function called `_inflate` are none of them decoders, and none of them fills a
cell: `SQUASHFS` lists XZ among its trial orders and has no XZ arm, so XZ is a
refusal; `PE32_PETITE` and `PE32_AUTOIT` call their decoders `_inflate` and
contain no zlib at all, so neither says Deflate.

A column no row in that table populates is not printed at all, so the large
legacy archive table stays as narrow as it always was. **An empty cell means
that type has not been audited yet - it never means "none".** Cells wrap
inside their column rather than stretching the row, so the output stays
readable on a narrow terminal; the widest line is 149 columns.

### Machine-readable

`--json`, `--xml`, `--csv` and `--tsv` carry the same fields - `id`, `name`,
`versions`, `codecs`, `notSupported` and `classes` (the table membership as
stable lowercase tokens such as `packer-pe32`, `installer-pe64`, `sfx-elf`) -
so a consumer can rebuild these tables itself:

```json
{
    "classes": [ "archive" ],
    "codecs": "Copy, LZMA, LZMA2, PPMd, BZip2, Deflate, Deflate64, Zstd, Brotli, LZ4, LZ5, Lizard, BCJ, BCJ2, ARM, ARMT, ARM64, PPC, SPARC, IA64, Delta, AES-256",
    "id": "7ZIP",
    "name": "7-Zip",
    "notSupported": "RISC-V filter (codec 0x0B)",
    "versions": ""
}
```

### Where the two disagree

The grouping, the IDs and the codec/version/refusal cells are generated from
the type registry (`XBinary::FORMATINFO` in `_mylibs/Formats/xbinary.cpp`) at
run time, so they cannot drift from the build. Every populated cell there was
read out of the reader it describes. This document is maintained by hand and
exists to record the *narrative* scope of each reader, which the generated
tables cannot carry. Where the two disagree about whether something is
supported, the binary is right and a row here is stale.

One thing the generated tables cannot split, because the type registry has a
single `FT` for each: `.zip` and `.zipx` share `FT_ZIP`, `.lha` and `.lzh`
share `FT_LHA`, and RAR 1.5-7.0 share `FT_RAR`. That is not a presentation
choice. The string `zipx` does not occur anywhere under `_mylibs`, and the only
per-format extension lists in the tree are the readers' own -
`XZip::getFileFormatExtsString()` returns `"zip,apk,apks,jar,ipa"` and
`XLHA::getFileFormatExtsString()` returns `"LHA(lha, lzs, pma, com)"` - so
there is nothing in the tree an extension column could be generated from. The
**Versions** and **Codecs** columns carry whatever distinction the readers
themselves make; for RAR that is the `RAR_50`/`RAR_70`/`RAR5 AES-256` entries
of the `FT_RAR` row.

Two extra columns describe codec coverage. **Codecs decoded** lists the
compression and encryption methods this build actually runs, under the name the
format itself uses. **Defined, not decoded** lists methods the format defines
that have no code path here; those are recognised and fail closed with an error
rather than producing wrong bytes. A `-` there means no further method was
found in the reader, not that the format defines none. Where a reader refuses
with one catch-all rather than testing methods by name, the cell says so - it
does not substitute a list of names read off the format specification.

The installer and self-extractor families are split by **carrier class** - the
executable (or script) the payload is attached to - because that is what decides
which reader sees the file at all. `XSFX`'s carrier gate accepts a DOS MZ image
(which is also what a PE and an NE start with), an ELF, an Atari GEMDOS `0x601a`
program, the Atari `EXEC` loader header (LHA probing only), and a raw DOS COM
image *whose file name ends in `.COM`*; there is no Mach-O carrier. A family that
one reader serves on several carriers therefore appears in several tables below,
with the same row name.

Two things the tables do not repeat in every cell: no stub is ever executed, and
a row that delegates to a native archive reader inherits that reader's method
table exactly - the Codec column names it in full so the delegation is not a
blank cheque.

### Executable packers and protectors

The former single "Executable packer / protector" table is split by **target image
class**, because a packer's scope is per image family: UPX handles seven of them and
its versions, codecs and output fidelity differ in each, so one merged cell could only
be vague. `-F/--filetype` IDs are given in the Identity column; the packer types are
reachable with `-F` today but are **not** listed by `-i` (see the note after the
tables).

`Codec` is the *packer's own* compression, not the container's. The `Extract` column
reads:

- **Yes** - the reader rebuilds a loadable image of the original program.
- **Analysis** - the reader rebuilds an image that is good for static analysis but is
  not runnable, because no usable import directory is produced. Four readers do this by
  mapping the decompressed sections into a fresh PE under synthetic `.clam01..` names
  with every data directory left zero (`xaspack.cpp:626`, `xfsg.cpp:344`,
  `xmew.cpp:489`, `xpetite.cpp:830`; measured on the rebuilt files - ASPack
  `.clam01..06` and MEW `.clam01/.clam02`, no non-zero data directory in either).
  Yoda is the exception in *shape*: it publishes the original header, the original
  section names and the surviving directories, and only zeroes the import directory
  (`xyoda.cpp:667`) - analysis-grade for the same reason.
- **No** - recognised and reported, but the rebuild fails closed. UPX-packed PE32 from
  UPX 0.60-0.84 is the one case in these tables that lands here.

No reader shells out to an external tool: `XUPX::_runUPXDecompress()` is a stub that
returns `false` (`xupx.cpp:3411-3419`), so every fallback is a visible failure rather
than a silent degradation. None of them runs the packed stub as *native* code either -
but three of them do **emulate** it, under a hard step budget, because the data they
need is only produced at run time: ASPack 2.11/2.11c decrypt a polymorphic stub head by
emulating from the entry point in `XEmuX86` with an 8,000,000-step cap
(`xaspack.cpp:86-117`, cap at `:91`, invoked at `:987-989`); newer Petite builds call
the stub's own embedded decoder inside the same sandbox under `PET_EMU_MAX_STEPS` =
100,000,000 (`xpetite.cpp:108-180`, cap at `:36`, invoked at `:638`); and Yoda's
per-byte decryptor is interpreted by a purpose-built byte-VM that understands about ten
opcodes and is bounded by both the stub's own counter and a jump budget
(`xyoda.cpp:167-256`). An emulation fault, a cancellation or a cap overrun aborts the
rebuild rather than publishing a wrong OEP.

`-F UPX`, `-F PE32_ASPACK`, `-F PE32_FSG`, `-F PE32_MEW`, `-F PE32_NSPACK`,
`-F PE32_PETITE` and `-F PE32_YODA` all work, and detection routes to them
automatically, but none of them appears under `-i`'s "Packed executables" heading -
in this build that table holds only `ISCAB` and `BZIP2SFX`, because
`XArchives::getArchiveOpenValidFileTypes()` (`XArchive/core/xarchives.cpp:648`) is the
set `-i` enumerates and it inserts only those two of the
`FT_FLAG_STATICUNPACKERS` types. The binary is still the authority on what it can
open; it just under-reports itself here.

Both tables below carry three extra columns. `Versions` is the generation range
the reader accepts. `Codec` is what is actually decoded inside the container, not
what the specification allows. `Defined but not supported` is the third state:
the format can carry it, this build has no code path for it, and such an input is
recognised and fails closed rather than producing partial or fabricated output.

Container identity is decided by content, not by the file name. The CUE route is
the single exception - it is the only row whose detection reads the target's
suffix.

One row per reader, except for package extensions that have no reader of their
own: `.war`, `.ear`, `.xpi`, `.xapk`, `.cbz`, `.appx`, `.msix`, `.whl`, `.odt`,
`.ods`, `.odp`, `.docx`, `.xlsx`, `.pptx`, `.epub` and `.crate` get one row each,
because for those the row documents what the extension actually opens as rather
than a reader. None of them has an entry in the type registry - `xfileunpackerc
-i` lists none of them, and no code in the tree tests those extensions. They open
through the ZIP or tar.gz reader, and a ZIP-based package is reported under a
stronger identity only when its content earns it. That identity chain is one
else-if ladder: APK Set, then APK, then IPA, then JAR, then plain ZIP - so the
first match wins and the rest are never tried.

**Detection order beats several readers below, and the binary is what the user
gets.** `XSFXGzipArchive` (`_mylibs/XArchive/installers/xsfxgziparchive.cpp`)
searches the whole file from offset 1 for `1F 8B 08` - offset 0 is left to the
plain gzip reader - and accepts the first candidate that inflates to completion,
within 4096 candidates and 64 trial inflates. Whatever the container was, the
file is then `gzip SFX` (`FT_SFXGZIP`) and the user is handed exactly ONE Deflate
member, named from the gzip FNAME field or, absent that, from the archive's own
name. Its test sits at `xformats.cpp:3124`, inside the `detectArc4Run1` helper
(`:2812`-`:3938`, a chain of `if (...) { insert; return true; }` blocks) that the
outer ladder calls at `:4386`. Two consequences, both from source:

- Ahead of it, and therefore immune: VHD, VDI, QCOW2, VHDX and NTFS
  (`xformats.cpp:4324`-`:4332`), Apple II 2IMG (`:4367`), and inside the helper
  BeOS package (`:3009`), FDI (`:3029`), PCM (`:3034`), ACT Apricot (`:3044`),
  CISO (`:3049`), Linux cloop (`:3054`) and romfs (`:3064`).
- Behind it, and therefore exposed: VMDK (`:3179`), TeleDisk (`:3199`), VICE x64
  (`:3209`), OpenVMS PCSI (`:3264`), TR-DOS (`:3299`), CopyQM (`:3349`), Solaris
  package datastream (`:3439`), Compaq ROMPAQ (`:3449`), OS/2 PM Diskcopy
